## 目标与使用方式

请先检查当前代码、`AGENTS.md`、GitHub 最新版本、Release 和 CI，再执行开发。不要假设当前版本仍为 3.0.0，也不要把 README 的描述当成已经验证的事实。

以内置 FFmpeg 为核心，补齐编码 A/B、离线编码复测、跨平台分发和验证，同时完成真实宿主验收、测试可靠性、持续集成、文档与截图四项收尾，使项目接近可稳定交付的“95% 完成度”。

“95%”只是方向，不是可自行宣布的成绩。最终必须逐项报告验收证据、未完成项和实际限制。

## 一、范围与工作原则

1. 保留现有响度、真峰值、文件 QC、参考播放和默认逐位旁路行为。
2. 维持现有界面风格和中文文案语气，不做无关重设计。
3. 用户安装后即可使用 AAC / MP3 编码 A/B 和 CLI 编码复测，不需要安装 Homebrew、配置 PATH 或手动安装 FFmpeg。
4. 编码仅在用户明确请求时执行，全程本地处理，不覆盖源音频。
5. 先给出简短的调查结论和实施顺序，然后持续实施、测试、修复直至交付。只在缺少必要信息或权限时提问。
6. 执行本指导时的授权范围包括修改代码、构建、更新文档与截图、提交并推送 GitHub，以及发布通过验收的版本。不得覆盖用户已有改动、强推或移动既有发布标签。
7. 不扩展 AAX、DDP、多声道等无关功能。优先完成既有功能的可靠性和交付闭环。
8. 没有硬件、宿主、证书或账号时，准确记录限制，不得伪造测试、签名或发布结果。

## 二、先审计并复现问题

重点检查以下位置，路径以当前仓库为准：

- `Source/file/CodecCheck.cpp`

确认并记录：

- GUI 与 CLI 是否重复实现 FFmpeg 查找、启动和错误处理。
- 编码失败是否可能被测试误判为 `skipped`。
- CI 是否在相关测试之前准备好依赖。
- 编码 A/B 是否真实对齐时间、处理编码延迟并平滑切换。
- 取消、换文件、关闭窗口、销毁插件时是否存在残留任务或临时文件。
- 音频回调是否涉及锁、分配、文件 I/O、启动进程或等待。
- Windows 安装路径修复和安装冒烟测试是否仍然有效。
- 安装器、签名、截图和 README 是否与当前版本一致。

先建立基线并复现发现的问题，再做针对性修复。静态审查发现与运行时复现必须区分。

## 三、随包内置 FFmpeg

采用“可再分发的精简 FFmpeg 可执行程序 + 后台子进程”方案，优先复用现有编码流程。

1. 固定 FFmpeg 和依赖版本，记录来源、校验值、构建参数和补丁，提供可复现构建脚本。
2. 覆盖 Windows x64、Windows ARM64、macOS arm64 / x86_64。
3. 保留现有输入链路、AAC / MP3 编码解码、PCM、所需容器和重采样能力。根据实际链路决定精简范围，不要误删必要组件。
4. 禁用不需要的视频和网络功能，不随包附带无用工具。
5. 检查最终构建及外部库许可证，避免不可再分发的 nonfree 配置。发布相匹配的许可证、第三方声明、源码和构建信息。
6. 检查运行依赖，确保程序没有意外依赖开发机的 Homebrew、DLL 或 dylib。
7. macOS 按嵌套代码规则安放辅助程序，先签内部代码，再签外层包。没有 Developer ID 或公证凭据时明确记录，不得冒称完成公证。
8. 插件包视为只读，不在安装目录生成缓存、输出或更新 FFmpeg。

选择适合 VST3、AU、Standalone 和 CLI 的部署位置：

- 使用共享运行时时，验证单独安装、升级、卸载及多个版本共存。
- 各自携带运行时时，说明体积代价。
- 无论采用哪种方式，都必须保证所发布的每一种使用形式可以独立正常工作。

## 四、统一运行时与进程管理

实现统一的 `FFmpegRuntime` / `CodecBackend` 或等价模块，由 GUI、CLI 共用。

- 默认优先使用随包版本，不依赖 PATH。
- 如保留用户覆盖路径，必须显式配置、验证能力并显示来源；错误不得静默回退而掩盖配置问题。
- 根据当前插件模块定位路径，避免把 DAW 的可执行文件路径当成插件路径。
- 使用参数数组启动，正确处理空格、中文、Unicode 和特殊字符，不拼接 shell 命令。
- 检查可执行权限、架构和必要编码器能力。
- 在后台持续消费有界 stdout/stderr，避免管道堵塞，保留有用错误信息。
- 支持进度、取消、超时、退出码和输出有效性检查。
- 区分运行时缺失、无法启动、输入损坏、编码失败、磁盘不足、写入失败、取消和超时。
- 超时策略适应长文件，区分处理缓慢与长时间无进展。
- 插件销毁后不得有回调访问已释放对象，也不得留下孤立进程。
- 多实例使用独立任务标识和临时目录，限制并发资源占用。
- 成功、失败、取消和异常退出后的临时文件均有明确清理策略。

## 五、补齐编码 A/B 的实际体验

1. AAC 256k / MP3 320k 均真实编码、解码并重新测量。
2. 验证编码器延迟、首尾 padding 与时间映射，不能仅因两个播放器设置了同一秒数就宣称对齐。
3. A/B 共用播放时基，验证连续切换、seek、循环、暂停、恢复和 EOF。
4. 使用短交叉淡化避免切换爆音，并定义切换期间的电平行为。
5. 等响比较可开关，显示实际补偿值，避免与参考匹配或其他 trim 重复叠加。
6. 明确显示原始 / 编码后、编码规格、进度、当前监听来源和失败原因。
7. 输出 ΔLUFS、ΔTP、文件大小、源文件与产物哈希、FFmpeg 版本及配置标识。
8. GUI 和 CLI 使用一致的测量与报告字段，保持已有报告兼容性。
9. 缓存绑定源文件内容、编码设置和后端版本。源文件变化后，旧结果不得继续显示为有效。
10. 临时音频使用可写缓存目录，支持长文件流式播放，避免整段解码导致内存随时长增长。
11. 关闭编码试听后恢复既有监听状态，默认不开启任何音频处理。
12. 切换文件、重新编码和取消任务时，旧任务结果不得覆盖当前文件的新状态。

## 六、修复“测试失败却绿灯”，补齐自动化验证

### 失败与跳过规则

- 正式安装包必须包含 FFmpeg，找不到或无法使用应使测试失败。
- 开发环境的可选依赖跳过只能针对已确认的依赖缺失。
- 编码错误、解码错误或输出损坏必须失败。
- 报告分别统计 `passed / failed / skipped`，不把 `skipped` 算成通过。
- 验证测试自身能正确失败：注入不可启动的运行时、失败退出码或损坏产物，确认门禁确实拦截。

### 测试覆盖

- AAC 和 MP3 各自的编码、解码、测量、GUI 状态和 CLI 退出码。
- 没有系统 FFmpeg、没有 Homebrew、PATH 不包含 FFmpeg 时仍正常工作。
- 中文与空格路径、单声道/立体声、不同采样率、短文件与长文件。
- 损坏输入、只读输出、运行时缺失、进程失败、取消、超时和多实例。
- A/B 时码、编码延迟、切换连续性、增益与旁路恢复。
- 音频回调零分配、无阻塞，检查共享状态的线程安全。
- 安装、覆盖升级和卸载，确认 Windows VST3 目录仍正确。
- 最终安装产物在干净环境中的运行依赖与编码器能力。

先定义适合测试信号和编码方式的误差容限，并说明依据。不得为让测试通过而随意放宽容差。

## 七、真实宿主与长时间运行验收

这一部分必须独立执行，不能由构建、离屏截图或虚拟文件测试代替。

### 目标宿主矩阵

| 平台 | 宿主 | 格式 |
| --- | --- | --- |
| macOS | Logic Pro | AU |
| macOS | REAPER | VST3 |
| Windows x64 | REAPER | VST3 |
| Windows x64 | Cubase | VST3 |

macOS Intel / Apple Silicon、Windows ARM64 的实际覆盖分别记录。

### 每个可用宿主的验收操作

1. 插件扫描、加载、卸载与重新扫描。
2. 播放/停止、定位、循环和 EOF。
3. 采样率与缓冲区大小变化。
4. 多实例同时使用。
5. 工程保存、关闭、重新打开后的状态恢复。
6. 插件窗口关闭与重新打开。
7. 编码过程中取消、换文件、关闭工程或移除插件。
8. 默认旁路、监听状态恢复和输出峰值。
9. A/B 时码、编码延迟与切换听感。
10. 频段独听、选区等响、参考播放与编码 A/B 之间的状态切换。

### 长文件验收

- 使用真实 ≥2 小时音频完成定位、循环和 EOF 检查。
- 至少进行一次连续 2 小时播放，记录内存、CPU、欠载和异常。
- 设定合理资源预算，检查是否存在持续内存增长。
- 虚拟两小时文件测试仅验证逻辑，不能替代真实文件和持续运行。

每条结果记录系统、架构、宿主版本、构建提交、操作步骤及证据。

无法执行的项目标记“未验证”，并说明缺少什么条件。自动波形检查与人工听感检查必须分开；没有真实试听就不得宣称听感验收通过。

## 八、让每次代码改动都有自动门禁

- 为普通 push / PR 增加适当的构建和快速回归，不再仅依赖标签发布时检查。
- 发布时执行完整 DSP、CLI、布局、编码往返及安装测试。
- 先准备随包运行时，再执行需要它的测试。
- 对最终安装产物运行测试，而不仅测试构建目录。
- 持续执行独立测量对照，明确区分生成信号与 EBU 标准素材。
- 在素材许可和获取条件允许时，将 EBU 标准素材验证纳入正式发布流程；缺失时明确记录，不能声称已经覆盖。
- 上传测试报告和失败诊断，不上传用户音频。
- 所有必需任务成功后才发布正式 Release。
- 核验版本号、标签、构建提交、包内运行时版本和 `SHA256SUMS` 一致。
- 检查必需任务没有因条件错误而被跳过。

没有对应硬件、宿主或凭据时，完成能够执行的工作并精确列出未验证项。不得将交叉构建称为 ARM64 实机验证。

关键验收未完成时发布 prerelease，不标记为生产验收完成。
